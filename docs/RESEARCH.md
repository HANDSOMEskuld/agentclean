# Storage semantics research

Research date: 2026-09-30. Scope is directory names and documented semantics only. No credential, transcript, message, or file-content inspection was performed. Paths are platform-sensitive; rules use environment expansion and must not treat a missing path as evidence that a path is safe.

## Safety interpretation

- **Rebuildable** means upstream documents describe the item as a cache or provide a supported purge/re-download path. It does not mean deletion is harmless while a process is using it.
- Configuration, authentication, session/transcript, history, state databases, installed tools, checkpoints, and unknown directories are **not cleanup candidates** by default.
- Active processes, lock/WAL/journal companions, and any path whose meaning is version-sensitive are excluded from destructive cleanup.
- Docker volumes are data stores, not caches. They are never automatically cleaned.

## Docker

Docker's object model separates images, stopped/running containers, networks, build cache, writable layers and volumes. `docker system prune` excludes volumes by default; `--volumes` adds anonymous volumes, while `docker volume prune --all` can remove unused named volumes. A volume can contain databases, source, credentials or application state and is not safely inferable from age or name.

**Policy:** inventory only by default; never recursively delete Docker's storage directory, never clean mounted host paths, and never automatically prune volumes. Any future cleanup must call Docker's own API/CLI, enumerate exact object IDs, detect running/attached use, show labels and require explicit confirmation. Build cache and dangling images may be separately offered as rebuildable candidates, but not without daemon/API verification.

Sources: [Docker pruning](https://docs.docker.com/engine/manage-resources/pruning/), [volume prune](https://docs.docker.com/reference/cli/docker/volume/prune/)

## Local inspection performed

The repository plan records these observed top-level names only: `/root/.claude` has `cache`, `sessions`, `projects`, `history.jsonl`, `settings.json`, `backups`, `plugins`; `/root/.hermes` has `cache`, `sessions`, `logs`, `image_cache`, `audio_cache`, `state.db` and WAL, `source`, `skills`, `auth/config`, `sandboxes`, `runtime`; npm, pip and uv cache roots exist. Codex, Cursor, Gemini, OpenCode and Cline were not present at the checked common roots. No contents were opened.

## Evidence gaps and version sensitivity

- Cursor's local layout was not sufficiently documented by an authoritative source; it remains analysis-only.
- Codex's repository docs establish configurable home and session storage, while some detailed path descriptions are from upstream discussions/issues; treat exact filenames as version-sensitive.
- Gemini and OpenCode expose documented paths/commands, but temp/database schemas and retention details can change; rules intentionally avoid recursive deletion.
- Cargo and pip explicitly warn that internal cache structures may change. Rules target documented roots/subcommands, not guessed child names.
